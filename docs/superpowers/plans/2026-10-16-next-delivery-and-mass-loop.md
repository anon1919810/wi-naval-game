# 交付收口与整炮组估重闭环 Implementation Plan

> 状态：三个单元均已完成本地独立验收，统一记录见 ../../plimsoll-1.0/delivery-mass-loop-2026-10-16.md。Codex 定范围、审查与独立验收；自包含实现交给 OpenCode。免费提供方恢复后使用原免费模型，没有切换付费模型。未提交、推送或部署。

**Goal:** 先完成当前总重、装甲尺寸、鱼雷空间三个单元的交付，再将整炮组来源估重接入可追溯的采纳闭环，随后实现五类固定装甲区域的分段、分层平板几何及采纳。

**Architecture:** 保留唯一重量台账与现有采纳事务。整炮组来源总数与向两组目标分配的产品政策分别命名和版本化；同一目标不得同时收到旧逐行建议与新的整组分配建议。装甲几何使用独立物理方法重新计算完整板件输入，在所选区域替代经验质量，旧读数仅作比较。

**Tech Stack:** 现有 Python / FastAPI / React / TypeScript，无新运行依赖。

**Spec:** 收口见 `docs/superpowers/specs/2026-10-16-next-coverage-design.md`；采纳政策已具体化于 `../specs/2026-10-16-whole-battery-adoption-design.md`；装甲范围见 `../specs/2026-10-16-armour-panel-geometry-design.md`。

## 随后独立单元：扩大装甲设计能力

优先考虑分段装甲带和分层甲板的实际面积估重，包含用户明确的倾角／高度定义及厚度、材料密度来源。新几何模型与原 SPS 经验估重分别显示、分别命名；同一装甲区域只能选一种质量模型进入台账。

先交付一套可编辑、可比较、可采纳的装甲方案，再逐步扩大区域与形状。倾斜装甲的重量变化不能只凭现有告警角度推导；倾斜板的实体几何、覆盖和防护效果也不能混为一项“已经覆盖”。真实 Queen Mary 的输入校准另需可追溯资料，不把受控算例当作实船证据。

## 集中验收节奏

每个功能单元结束运行一次相关核心与工作流批次；共享 UI 稳定后执行一次前端验收及构建；交付前走一条真实保存—计算—预览—采纳—重算—重开链路。只有代码变化、实际失败或未解决风险才重复检查。汇报优先说明用户能完成什么、还有什么缺口，测试数字放在证据里。
