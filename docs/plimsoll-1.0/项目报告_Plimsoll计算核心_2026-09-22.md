# Plimsoll 计算核心项目报告

日期：2026-09-22。用途：本轮收尾、评估现状与安排续接。

**结论：主要计算模块及数据基础已建立，统一入口和命令行正在整合；尚不能宣布类 SPS 计算核心全部完成。** 本轮按用户最新要求收束并交接，不继续增加界面、打包或服务器部署工作。本文将模块完成、整合完成、验证完成分别说明。

## 1. 项目定位与本轮范围

Plimsoll 是一战海战项目配套的通用舰船设计与载荷分析计算器，Queen Mary 是示范案例。游戏继续使用 Unity；本轮 Python 计算核心保持独立，不改写游戏战斗系统，也不以更换引擎为前提。

当前需要交付的是项目与重量账本、载荷浮态、静水力与稳性、简化连通进水、武备/装甲/动力关联、阻力/功率/续航，以及 Python API、单工况/批量/扫描 CLI 和 JSON/CSV。用户已将图形界面、网页服务、服务器部署和独立安装包后移。

完整耐波性、有限元与结构强度、历史造价、海战穿深/爆炸/碎片求解未纳入这一阶段。现有结果不能作为“全面超越 SPS”或实船设计认证的证据。

## 2. 已完成的组成部分

以下项目已有实现、针对性验证和独立代码审查；仍需通过最终整合验收。

| 部分 | 已有能力 | 实际意义 |
|---|---|---|
| 数据契约 | 统一项目格式、单位/坐标、结构化诊断、迁移、输入指纹、来源与估算 | 不再把缺值当零，来源不明不能自动变成史实数据 |
| 重量与载荷 | 分类账本、质量及三轴重心、按工况覆盖、质量矩、区间传播、重复计重检查 | 正常、满载和自定义条件使用同一重量权威 |
| 完整案例 | 方箱、通用汽船、Queen Mary 自包含项目及确定性生成器 | 核心不依赖固定舰名或工作目录猜测 |
| 浮态与稳性 | 耦合吃水/纵倾/横倾、残差、GM/GZ、开口限制、采样边界 | 分开报告求解收敛与物理适用性 |
| 几何分析 | 显式参考船型、所选水面下的几何量、Bonjean/静水力表、甲板间隙 | 设计水线结果与实际载荷水面不再混用 |

| 项目文件与型线导入 | 原子保存重开、显式内容导入、字节摘要、严格 JSON 与几何校验 | 导入失败保护旧文件；不会自动寻找替代型线 |
| 包与导出 | 普通 Python 包导入、旧脚本兼容、完整 JSON、保留路径与类型的 CSV、原子写入 | 导出成功不改变计算是否有效的状态 |

## 3. 当前整合工作

统一入口 `analysis.compute_project` 已进入实际计算测试，目标是将同一选定工况的重量、系统、几何、浮态、GZ、阻力、动力、续航和进水结果组织到统一阶段结果中。质量修订应用还要拒绝过期或伪造建议，保护基础账本及其他工况。

统一入口和新 CLI 已保存为本地检查点 **`1752467`**，提交明确标记为 WIP，尚未独立审查。协调入口相关 57 项针对性测试通过；CLI 的 6 项针对性测试通过，实际验证了加载工况批量运行和失败后继续处理。

CLI 的真实单工况完整矩阵、成功的 3×2 扫描及部分错误处理还未验完，`import-geometry` 只有参数入口、尚无处理函数，命令行文档也未完成。不能将已列出的命令名当作全部可用功能。详细续接风险见配套交接文档和已归档检查点报告。

## 4. 尚未完成的计算与覆盖

七页原始清单共 191 条记录（184 条页面项及 7 条公共控件）。收尾的暂定映射中，53 条有现存输入/结果路径，101 条仍需补投影、输入定义或适配；另有 26 条原批准排除项、10 条后移的展示控件、1 条未拍摄完整的炮组编辑器观察项。**这些是页面记录数，不是算法数、工时比例或最终验收数量。** 当前已识别的主要缺口是：

1. 炮、炮座、弹药和旋转装甲的分类合计，以及独立的单舷投射弹重；必须遵守账本包含/排除边界。
2. 多组鱼雷、水雷、深弹和按位置分类的杂项载荷，其携带量、再装填与布置等字段仍需完整的类型与绑定。
3. 装甲带、甲板、司令塔的分组/分段投影与合计，不能把共享质量重复计入。
4. 所选载荷的横摇周期/GM 与设计水线的经验显示项需明确区分；不得将旧 L0 输出冒充加载结果。
5. 正常、满载、标准和轻载的多工况对应；后两者必须显式定义，不可猜测扣除载荷。
6. 甲板分段端点净空及长度百分比的完整投影；缺失分段保持未知。
7. 固定功率/预测功率模式、可变载荷分类及真正的目标纵倾约束，还需明确请求语义；求解初始猜值不能冒充目标约束。

另外，“最小主装甲带长度”尚无获准的计算代理，不能臆造 SPS 算法或填一个占位数。完整暂定映射已归档为 `evidence/seven-page-binding-proposal.json`，不代表这些未完成项已实现。

此外仍需完成统一入口/CLI 的独立审查、实际结果导出整合、Queen Mary 非零时长破损时间线、完整回归和性能记录。

包导入修正有 140 项针对性测试，导出器有 9 项针对性测试，且均通过独立审查。已有独立物理验证包含方箱/椭球、倾斜液体守恒、进水步长收敛及阻力公式基准；它们不能证明历史输入的精度。

完整的验收清单共 45 项原始要求，其中 35 项保留为核心要求、6 项保留计算部分并后移展示、4 项由用户后移。该清单尚未被全部标记为验收通过。

## 6. Queen Mary 数据可信度

工程账本正常质量为 27,851.62934079477 t，满载质量为 31,926.26200617077 t。多位小数仅用于复现；型线、部分重量和重心仍为工程估算。没有加入任意补差重量制造历史吨位吻合。

模型包围盒面积不等于装甲真实展开面积。缺少原始型线与重量重心档案，是数据精度的主要限制。Holtrop 比较还需区分所选水线长度与模型全长；声明的纵倾/端点代理必须标为估算、非主结果，不通过放宽检查或调参获得表面吻合。

## 8. 游戏是否需要全部完成这些计算

**当前游戏阶段不需要以完整 Plimsoll 为前置条件。** 独立舰船设计工具的完整性，已超过灰盒垂直切片和可信损伤试验场所需。更复杂的计算只有在影响玩家决策、损伤反馈或数据一致性时，才应成为当前研发优先项。

| 优先级 | 建议保留的用途 | 暂缓完善的部分 |
|---|---|---|
| 游戏必需 | 统一质量/重心/载荷与单位；舱室进水、浮态和失稳反馈；模块损伤对火力/动力的影响；可复现诊断 | 不应因设计页面尚未齐全而阻塞这些能力 |
| 离线辅助 | 利用已有静水力/GZ及阻力/功率计算生成与核对舰船参数、比较载荷和损伤工况 | 无需把全部求解放到游戏每帧运行 |
| 独立设计工具完善 | 完整七页绑定、多组任意武器/装甲设计、多方法精细对照、通用批量设计流程 | 可在游戏闭环稳定后继续，不作为当前游戏可玩的门槛 |

建议现在固定可复核检查点，暂停新增设计工具功能，把后续重心转向“舰船受损 → 舱室/系统变化 → 浮态与航速/火力变化 → 玩家能理解”的游戏闭环。已有 Python 核心保留作离线依据，Unity 运行时采用经验证、满足实测性能预算的更新方式。接入前仍须读取 Unity 最新代码，本文不声称该链路已经全部存在。

这是针对用户收尾时提出“项目是否需要如此拟真系统”的技术建议，**不是已经批准的范围删减或验收通过**。若仍选择完成独立类 SPS 工具，下一轮按“协调入口/CLI → 七类绑定缺口 → 联合回归与性能 → Web”继续。若选择游戏优先，应另行明确最小可玩验收，保留原要求为后续路线。

正式“已完成”通知尚未发送；此前微信消息是用户要求的通路测试。收尾时核对目标系统为 `paused`，本次报告交付不恢复长期功能扩展，也不将开发目标标为完成。
